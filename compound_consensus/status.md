**Version: 1.1 — by Albert Sheng**

**用途**：讓新的 session 快速接手**第三支應用**（跨重複樣品的化合物共識）。

## TL;DR

- **可用，端到端跑得動。** Coffee-bean 實測：18 檔 → 81 個共識區域 → 依票數
  排序的化合物清單。介面三個模式，而**模式本身就是流程的三個步驟**：
  看熱圖選峰 / 選擇相似 mea / 看共識化合物。工具列只有「選資料夾」。
- **驗收狀態**：1.0 的介面使用者實跑驗收過（2026-08-31）。**1.1 的最後一批
  （模式即步驟、基準欄、進度視窗、灰掉未達條件的模式）尚未經使用者實跑**——
  接手時先照 `TEST_PLAN.md` §5 走一遍。
- **與前兩支完全隔離**：不修改任何既有 `.py`，產物一律帶 `3` 或放自己的命名空間。
- **239 項測試**（`test3/`），全套 477 項通過。幾乎每一項都是**實際踩過的錯**的
  回歸測試，不是湊覆蓋率。
- **自動分組準確度 43/45 = 96%**（三個資料夾、最近鄰同組）。
- **鑑定能力有硬上限**：漂移庫只涵蓋 84 個化合物，見下。

## 這支在做什麼（一段話）

使用者挑出**同一個標本**的多個 `.mea`（重複測量），本應用把每個檔的化合物候選彙整
起來，依「有幾個重複支持」排序。**這是 VOCal 與第一支應用都不做的一步**——反編譯
VOCal 0.4.31.412（461 個混淆類別 + 7 個外掛）確認：它的 `Compounds` 每一筆只綁一個
`.mea`（實測 0/28 參照超過一個檔），化合物身分是操作者逐檔手動標的。

## 1.1 加了什麼（2026-09-07）

使用者的觀察：**逐檔挑峰時看不到峰對到什麼化合物，等於閉著眼睛選。**
1.0 的峰表只有 `# / On / Drift rel / RI / 強度`，而第一支應用還有
`GC×IMS / GC / IMS / ▶` 四欄。

1. **進入點 `main3.py`**（根目錄）。`python -m compound_consensus.app` 仍然有效，
   但使用者不必再知道那件事；直接跑 `compound_consensus/app.py` 會壞的理由寫在
   檔案開頭，`test3/test_main3.py` 把它釘成可執行的事實。
2. **逐峰比對四欄**，與第一支同語意。背景比對、依 `(檔名, rt_index, dt_index)`
   快取；**還沒比對顯示「…」、比過沒命中才顯示「—」**——兩者混用會讓使用者
   把還沒算完的峰當成沒有候選而關掉。
3. **▶ 候選視窗**：GC+IMS / 只有 GC / 只有 IMS 三組可各自開關，綠底＝兩軸都同意。
4. **共識表的維度標籤**從 `2D`/`RI` 改成 `GC+IMS`/`GC`/`IMS`/`混合`，
   **逐候選也有自己的維度欄**——同一個區域裡有些候選兩軸都對上、有些只有 RI。
   共識表另加 **Drift rel 與 RI 兩欄**：每一列講的是熱圖上的一個位置，位置就是
   （x = 相對 RIP 的漂移、y = RI）。原本只給 RT s，使用者對不回圖上哪一個圈——
   而且熱圖的 y 軸畫的是 RI，不是保留時間。`候選` 欄的意思（容差窗內有幾個
   化合物對得上）寫進面板下方的說明：1 跟 38 的意義天差地遠。
5. **新增 `ims_only` 這一層**：RI 沒對上但漂移對上時回報 IMS 候選，
   不再顯示「（無候選）」。放在最後一層，既有的 combined / gc_only 行為不變。
6. **門檻預設改成 1/2**（超過一半的重複看得到）。
7. **視窗預設攤滿螢幕**。
8. **預處理的失敗會講出來**（見下表最後一列）。
9. **彙整真的用使用者的勾選了**——修之前沒有，見下表。
10. **模式 2 的右側面板改成「這一組的體檢」**。原本列成員與相似度，兩欄跟左側
    檔案面板一字不差（使用者指出的）。改成放左邊看不到的：最低/平均相似度、
    **離群的是哪一個檔**、門檻換算成幾個檔、還要找幾個檔的峰。判定走
    `L.group_stats()`，與彙整前的確認對話框**同一個來源**。
11. **模式 2/3 的熱圖唯讀**：那兩個模式的右側不是峰表，點掉一顆峰完全沒有回饋。
    左上角有標記說明，縮放平移照舊（那只是看，不改狀態）。
12. **檔案面板加狀態欄**（使用者指出「按 2 掃描才有」不專業）。
    `就緒`／`待找峰`（有 `.npz`，約 55 秒）／`未處理`（約 68 秒），
    **點狀態欄＝不管有沒有都重做一次**（會先問）。**三態不是兩態**：只看 `.npz`
    的話，有 `.npz` 但沒找峰的檔會顯示成就緒而點下去仍要等 55 秒——說謊比不說更糟。

    - **顏色用自己畫的圓點，文字同時保留。** 走過三種做法：
      (1) 🟢🟡🔴 —— Windows 的 Tk 退回**單色字形**，三種狀態長得一模一樣
      （使用者實測回報「每個檔看起來都一樣」）；
      (2) tag 的前景/背景 —— 只能染**整列**，染不了單一格；
      (3) ✅ **item 的 `image`** —— 用 `PhotoImage` 就地畫一顆圓點放在檔名前面，
      真的有顏色而且不依賴任何字形。圓外**完全不塗**（保持透明），圓點才會浮在
      該列自己的底色上；想用 `{}` 表示「不塗」會得到 `can't parse color ""`。
      **圖片參照一定要留住**（`self._dots`）——被 Python 回收之後畫面上那張圖
      會直接消失而且不報錯。
      文字仍然保留：顏色不該是唯一的資訊來源（色覺差異、螢幕擷圖、黑白列印）。
    - **相似度欄的空值不可以寫「待掃描」**：那和狀態欄、和「2. 掃描全部」按鈕撞在
      一起，已經找過峰的檔看到它會以為峰沒找完（使用者實際回報）。改成 `未計算`
      ——那一欄講的是**跨檔**相似度還沒算，光有這個檔的峰不夠。
13. **逐檔規則**（`rules_store.py`）。兩層：`rules_config.json` 是**預設**，
    某個檔另有主張時就留一份自己的；解析時先找覆寫，沒有才用預設。
    規則面板有**套用範圍**選擇，**預設「全部檔案」**（使用者要求：改規則本來就該
    套到所有 `.mea`）；切成「只有目前這個檔」才寫逐檔覆寫。另附
    「套用到選取的檔（N）」與「本檔改回預設」，有自訂的檔在清單上標 `[自訂規則]`。

    - **兩層的壽命刻意不同**（使用者要求，經過一次反覆）：

      | | 存在哪 | 關掉程式之後 |
      |---|---|---|
      | 預設 | 記憶體（起點是 `rules_config.json`） | **歸零** |
      | 逐檔覆寫 | `results/<base>_rules3.json` | **留著** |

      理由：改「全部檔案」是**這一輪想怎麼看**（調 `top_n` 看看少幾顆峰），下次
      打開不該還黏著——使用者原話「top_n=10 不是預設」。把某個檔**特別**調成
      不一樣則是對那個檔的**判斷**（這批訊號弱、那個檔 RIP 拖尾），重開一次不該
      要人重做——使用者原話「once they are customized their own rule will be
      overwritten」。要讓預設也長期改變，用「存成共用預設」寫回
      `rules_config.json`（會先問——那一份**三支共用**，`main.py` / `main2.py`
      也會跟著變）。
    - **每一個影響偵測的呼叫都要走 `_rules_for(mea)`。** 傳錯 config 不會報錯——
      `params_fingerprint()` 會忠實地替錯的參數記一份指紋，快取於是無聲地對應到
      別人的設定。這是逐檔規則唯一的風險點，`test_rules_store.py` 釘住它。
    - `consensus_regions()` 多了 `rules_for` 參數；掃描與彙整都傳。
    - **只有強制規則（R004/R006）進指紋**：它們在突出度門檻之前生效。選配規則
      （R001/R002/R003/R005）只標記，改了不該讓 18 個檔各重跑 55 秒（約 16 分鐘）
      換來一模一樣的峰。這是刻意的，有測試守著兩個方向。
    - `effective()` 一律回**深拷貝**：共用同一個 dict 會讓改 A 檔把 B 檔一起改掉。
14. **圈只有兩種樣式**：選了＝實線紅，沒選＝實線灰。原本救回規則否決的峰時畫
    紅色虛線，使用者回報看起來像畫錯了。那個區別留在表格（琥珀色），
    那裡有欄位標題可以解釋自己。
15. **檔案面板加「基準」欄**（使用者提議）。點一列的 ◉ ＝以它為相似度的比較
    對象，相似度 ≥ 0.80 的檔自動被選進這一組；換一個基準就**整組重挑**（不是
    累加）。**一次只有一個基準**——相似度是相對量，兩個基準就沒有一欄數字可以
    並排比較。

    - 原本基準是**隱含**的（`self.current`，最後點過的那個檔）：使用者看不出
      自己在跟誰比，而且在模式 1 點檔案看熱圖會順手換掉整欄的比較對象。
    - **點基準就開始算相似度**，不必再去按別的按鈕（使用者回報過「選了 base
      但整欄還是未計算」）。所需的東西——每個檔的峰——多半早就備好了。
    - 相似度還沒算就設基準：挑不了整組，但**基準本身要進去**，否則看起來像
      沒有反應；算完會自動補挑一次。
    - 欄位序號因此全部後移（基準 #1、組 #2、狀態 #3、相似度 #4）。
      `on_files_click` 依序號分派，既有測試立刻抓到——這正是那些測試存在的理由。
    - 順手修掉標題的 `basename[7:-4]`：那寫死了 `YYMMDD_HHMMSS_` 前綴，檔名短一點
      就切成空字串（標題變成「相似度 vs 」）。改成只在真的看到那個前綴時才拿掉。
16. **與規則一致時不留下「意見」**：`_toggle_index()` 在新狀態等於 `rule_active`
    時存回 `user_active=None`，不是存一個明確的 True/False。見下表最後一列——
    這一條是規則失效期間累積出 75 筆假「意見」的直接原因。

17. **流程重整：模式**就是**步驟。** 工具列原本有「2. 掃描全部」「3. Consolidate」，
    左邊又有三個編號模式——同一條流程被寫成兩套編號，使用者得自己猜哪個先。
    現在工具列只剩「選資料夾」，切到模式 2 就算相似度、切到模式 3 就彙整。

    - **模式 2/3 在沒有基準之前是灰的**：沒有基準就沒有相似度，沒有相似度就挑不出
      同組，挑不出同組就談不上共識。灰掉比讓人點進一個空面板好——空面板看起來像壞了。
    - **`_cons_dirty` 旗標**：模式 3 只在**真的變了**時重算（組員／門檻／規則／選峰）。
      沒有它的話，模式之間切來切去每次都白跑一輪比對。
    - 相似度**永遠涵蓋整個資料夾**，不是只算選取的那組——只掃已選的是循環論證
      （得先知道答案才掃得到答案），1.0 就踩過。
18. **進度視窗**：跑得久的工作都有（相似度、彙整、重新產生、首次載入檔案）。
    用**不確定式**跑馬燈而不是百分比——這些工作的耗時差好幾個數量級（比對十幾秒、
    找峰每檔 55 秒），硬給百分比只會給錯的期待。沒有關閉鈕：關掉它並不會停止背景
    執行緒，留一個關得掉但沒作用的鈕比不留更糟。
19. **模式 2 改名**「選同標本這一組」→「選擇相似 mea」（使用者說原本的中文很怪）。

`library.py` 與 `library_data/` **一個字都沒動**（使用者 2026-08-31 的決定）。

## 隔離規則（改動前必讀）

1. **不修改任何既有 `.py`**。既有模組一律 import 後呼叫。
2. **不寫前兩支的產物**：峰的選取寫 `_peaks_state3.json`（不是 `_peaks_state.json`），
   指紋寫 `_peaks2_fp3.json`，自己畫的背景圖帶 `_c3`。**讀**它們的產物是允許的。
3. **不寫任何東西進 `GAS/`**：`use_sidecar=False`，`.mea` / `.gasprj` 唯讀。
4. **不用 subprocess**。第一支用 `[sys.executable, "peaks.py", ...]` 起子行程，那在
   打包成 exe 之後會變成用 exe 再開一次 GUI（`sys.executable` 是 exe，而 `peaks.py`
   不在磁碟上）。第二支已經改掉，本應用跟隨。

## 1.0 開發期間修掉的問題（症狀與原因差很遠的那些）

| 症狀 | 真正的原因 |
|---|---|
| 熱圖上**一個圈都沒有**，也沒有錯誤 | 背景圖 y 軸是 RI，而 `detect_one()` 只找峰不掛 RI → 28 顆峰全部 `ri=None` → 算不出座標 |
| 視窗只剩一條工具列 | `quit_app` 被插進 `_build()` 中間，建三個面板的程式碼變成 `destroy()` 之後的無法到達碼。**語法正確、import 成功** |
| 按「掃描」時整個視窗縮成一小塊 | 狀態列每個檔換一次文字，pack 把寬度變化傳到最上層；面板還空著時自然大小很小 |
| 掃描完 UI 凍住十幾秒 | 相似度在主執行緒算（`_drain()` 裡） |
| 相似度整欄「不在掃描範圍」 | 掃描只掃已勾選的那一組——但相似度是拿來**決定**分組的，循環論證 |
| 兩個檔的相似度永遠 −1.00 | 逐區域標準化在 n=2 時把每欄壓成 (+1,−1)，相關係數與資料無關 |
| 改了 `top_n` 表格變了、熱圖沒變 | 圈看 `active`，而 `mark_rules()` 寫 `rule_active`，兩個鍵沒接起來；**共識也照樣算進那些峰** |
| 預告 8 分鐘、實際跑 16 分鐘 | 估時看 `_maxima.npz`（第一支的快取），而偵測認的是 `_peaks2.json` |
| `--dry-run` 竟然會寫檔 | 採信既有快取會補寫指紋，而 `plan()` 在 dry run 時也跑 |

## 鑑定能力的硬上限（**接手前一定要知道**）

漂移庫（`.iml`）只涵蓋 **84 個化合物**，而 RI 庫（`.ril`）有 9,958 個。2D 命中需要
兩軸都對上，所以**RI 庫裡 97% 的化合物永遠拿不到 2D 命中**，RI 再準也沒用。

另有 213 個化合物的漂移資料**存在但沒有宣告 `DtMode`**，實測與已宣告的來源
**51/55（93%）吻合在 ±0.05 內**（中位差 0.0028）。接受它們會讓涵蓋變成 297 個（×3.5）。

**使用者 2026-08-31 決定：`library.py` 與 `library_data/` 一律不得修改**，所以這條
路關閉。完整數字與推導在 `README.md`。**這是考慮過並否決的方案，不是還沒發現的改進。**

因此本應用的目標是**一份誠實排序的候選短名單**，不是一個名字。

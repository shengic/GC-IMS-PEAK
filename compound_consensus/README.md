# 第三支應用 — 跨重複樣品的化合物共識

**Version: 1.0 — by Albert Sheng**
**最後更新**：2026-08-31

> 本 repo 現在有**三支應用**。前兩支見根目錄 `CLAUDE.md`。三支共用底層模組，
> 各自獨立演進。本檔自足：要了解第三支，讀這一份就夠。

---

## 這支在做什麼

使用者挑出**同一個標本**的多個 `.mea`（重複測量），本應用把每個檔案的化合物候選
彙整起來，依「有幾個重複支持」排序，給出最可能的化合物。

| | 第一支 `main.py` | 第二支 `main2.py` | 第三支（本應用） |
|---|---|---|---|
| 一次處理 | 1 個 `.mea` | 一整批 | **同一標本的重複測量** |
| 輸出 | 該檔逐峰的候選 | 區域 × 檔案 強度矩陣 | **跨重複彙整後的化合物清單** |
| 用途 | 看清楚單一樣品 | 比較 A/B/C/D/E 組 | 判定「這到底是什麼化合物」 |

## 為什麼需要它（證據，不是推測）

**VOCal 不做這件事**——2026-08-31 反編譯 `VOCal Release 0.4.31.412`
（461 個混淆類別 + 7 個未混淆外掛）確認：

- 全部類別中**沒有任何** candidate / consensus / vote / majority 相關字串。
- 化合物路徑全是單張圖操作：`Collect manual peak data`、`Create Peak`、
  `Filter Form: CAS/NAME/D_RI/D_DT`、`---no matches found---`、`Dual Column Search`
  （後者合併的是**兩根管柱**，不是多個檔案）。
- `.gasprj` 的 `Compounds` 每一筆只綁**一個** `.mea`（`FileInfos`）：實測 **0/28**
  參照超過一個檔案。格式本身沒有欄位可以記「這個化合物在 15 個檔案中有 12 個支持」。

VOCal **有**的跨檔自動化是：`AutoArea`（自動畫框）、`AlignmentTool`（保留時間對齊）、
區域×檔案矩陣、以及 `ML_Ensemble`／`AI_Ensemble`。最後一項容易誤會——`gO.class` 顯示
它的輸入是區域強度（`Peak Volume` / `raw intensity`），**目標是 `targetColorIndex`
（樣品的組別）**，也就是「這個樣品屬於哪一組」的分類器，與化合物身分無關。
兩個真實專案檔的 `AI_Ensemble` 都是 `None`，從沒被用過。

> ⚠ 早期的判斷「VOCal 的方框是手畫的」**是錯的**：`AutoArea` 存在，而 `.gasprj`
> 沒有記錄方框的來源，所以無法分辨。不要再拿「自動找框」當本 repo 的獨有優勢。

## 分組是可以自動判定的（實測 96%）

以「每個檔案的最相似鄰居是否同組」為準，跨三個資料夾 **43/45 = 96%**
（下表是 2026-08-31 加上「逐檔置中」之前的 41/45；置中之後鱸魚由 13/15 起算提升）：

| 資料夾 | 命中 | 未命中 |
|---|---|---|
| 藝妓咖啡 | 12/12 = 100% | 無 |
| Coffee-bean | 17/18 = 94% | `260623_182952_A_1_3` |
| 鱸魚 | 12/15 = 80% | `FM_3`、`EHM30_1`、`EHM30_2` |

**即使 96%，仍落在「可以建議、不可以替使用者決定」的區間**——所以 UI 是「自動highlight
候選、使用者可增刪」，不是自動分好。鱸魚的兩個未命中是 `EHM30 → EHM15`，同一種添加物
的不同劑量，屬於化學上合理的混淆。

同組重複的相關係數 r ≈ 0.88–0.98；**同材料不同次製備** r ≈ 0.56–0.67
（由 Coffee-bean A 組在 0629 重跑一次意外提供的參考點）。這個落差說明三個重複是
**分析重複**（同一份製備重複進樣），不是獨立製備。

### ⚠ 分組需要「區域」，不能只比熱圖

實測過最省事的做法——整張熱圖粗網格比對——**驗證失敗**（C 組 0.49，正確值 0.88），
因為大片背景會蓋過訊號。改用高變異數網格點有改善但仍與區域法不一致。
**必須先有峰／區域**，也就是偵測那一步（約 55 秒/檔，會快取）跑不掉。

## 隔離規則（沿用第二支，改動前必讀）

1. **扣過基線的資料絕不寫回共用的 `.npz`**——否則 `main.py` 會當原始值載入而無跡象。
2. **不寫任何第一／二支應用的產物**（`_peaks.json` / `_areas2.json` / …）。
   以函式呼叫既有模組，不跑它們的 CLI。
3. **不寫任何東西進 `GAS/`**——`.mea` 與 `.gasprj` 一律唯讀。
4. **不修改任何既有 `.py`**。既有模組只 import。

## 這支應用的現實上限

漂移庫只涵蓋 **84 個化合物**（見下方 2026-08-31 的量測），而 2D 命中兩軸都要對上。
所以本應用的目標不是「給出一個名字」，而是**給出一份誠實排序的候選短名單**——
這也正是未標的代謝體學的常態（MSI 把「推定鑑定」列為一個等級，不是失敗；該領域的
註解率平均約 7%）。

會提高可靠度的是：跨重複的支持度、2D（RI×漂移）同時吻合、以及把容差窗依實測收緊。
不會提高的是：把票數當成證據強度、或拿強度高低當鑑定依據（實測強度最高的區域反而
比較難鑑定）。

## 尚未決定

   一個分頁」不是加法——不是複製 2450 行，就是改動它的版面。**先寫 headless 的

2. **掃描時機**：建議「用已快取的、其餘按鈕明示」——開資料夾時檢查哪些檔已有
   `.npz` / `_maxima.npz`（第一、二支可能已經建好），有的立即可用，沒有的**灰階標記**
   並提供「掃描其餘」。**「沒掃描」絕不可以看起來像「不相似」**（同 `n_det=None` vs `0`）。

## 兩條必須守住的誠實界線

- **n=3 是分析重複**：可以報「有幾個重複支持」與「跨檔一致性」，**不能報 p 值**——
  那測到的是進樣重複性，不是標本間變異。
- **彙整提高的是可靠度，不是真值**：若 RI 尺標真的整體偏移約 300（見根目錄
  `status.md` open decision 3a），三個重複會**一致地**指向同一個錯誤答案，看起來
  更有說服力。輸出必須照樣帶 `ri_mode` / `assumed_unverified`。

## 2026-08-31 這一輪量到的事（不要重新推導一次）

### RI 是準的——問題不在尺標

拿操作者在 `.gasprj` 裡標註的 14 個化合物，比對「他記的 RI」與「我們用 6 點酮校正
在同一個 `Rt` 算出來的 RI」：**中位差 0.0，全部落在 ±5 以內**。

兩條完全獨立的校正路徑一致。所以先前懷疑的「RI 尺標整體偏移約 300」在**這批資料上
不成立**——鑑定失敗的原因在別處（見下）。`status.md` open decision 3a 談的是供應商
表格的極性，那是另一件事，仍然開著。

### 真正的瓶頸：漂移庫只涵蓋 84 個化合物

| 庫 | 列數 | 不同化合物 |
|---|---|---|
| RI 庫 `.ril` | 154,774 | 9,958 |
| 漂移庫 `.iml` | 1,000 | 298 |
| **實際可用於比對的** | **201** | **84** |

2D 命中需要兩軸都對上，所以 **RI 庫裡 97% 的化合物永遠拿不到 2D 命中**，RI 再準也
沒用。實測：操作者標註的乙酸乙酯，RI 庫裡有 469 筆、其中 115 筆落在我們量測的
±5 內，但漂移庫裡沒有可用的條目，於是候選清單裡根本不會出現它。

**為什麼只有 84 個可用**：`.iml` 有兩種方言，欄位版面**完全相同**（16 欄，
`Dt[a.u.]` 都在第 7 欄且都解析正確）——差別只在第 15 欄有沒有寫 `RIPrel`。
`match.match_drift_rel()` 要求 `DtMode == "RIPrel"`，於是沒宣告的整批被跳過。

> ⚠ 先前一度以為是「欄位錯位」（`DtMode` 讀到溫度、`T(IMS)` 讀到流量）。**那是
> 誤判**：兩種方言的欄位位置一樣，只是後者第 15 欄放的是溫度而不是模式字串。

**這些沒宣告的資料是可用的**：55 個化合物同時出現在兩種方言裡，漂移值
**51/55（93%）吻合在 ±0.05 內，中位差 0.0028**。兩個獨立來源對同一化合物給到小數
第三位一致，所以未宣告的檔案確實也在 RIP 相對尺標上。接受它們會讓涵蓋從
**84 → 297 個化合物（×3.5）**。

**使用者 2026-08-31 決定：`library.py` 與 `library_data/` 一律不得修改。**
因此這 213 個化合物維持不可比對，84 個就是上限。這是**已經考慮過並否決**的方案，
不是還沒發現的改進——要重開這個討論，先看上面的數字。

### K0：算得出來，但**刻意不用**

`resolve_calibrations_cached()` 會一併解出 `k0_mode=standard_based`，本應用只取
`ri`、丟掉 `k0`。起初是疏漏，但實測之後決定維持：

| | 候選總數 | 2D 命中的區域 | 只有 RI 的區域 |
|---|---|---|---|
| 不掛 k0（現況） | **401** | **46** | **3** |
| 掛上 k0 | 1507 | 36 | 13 |

`match_all()` 只要看到 `k0_value` 就優先用 K0，於是不再走 RIPrel；能兩軸吻合的區域
反而變少（46→36），掉到只有 RI 的那條路上，候選暴增 3.8 倍。呼應 `status.md`
open decision 4：**K0 ±0.05 是沒校準過的佔位值**。

### monomer / dimer 配對（`find_monomer_dimer_pairs()`）

同一個化合物在 IMS 會給兩個訊號：單分子（monomer）與雙分子（dimer）。兩者**同時**
離開 GC 管柱（保留時間相同），但 dimer 比較大比較重、**漂移時間比較長**。

不靠任何資料庫，只用這批檔案自己就找得出來：RT 相差 ≤6 s、drift 相差 ≥0.10、
**跨檔強度相關 ≥0.90**（最後這條是關鍵，與 LC-MS 那邊 CAMERA / RAMClust 分辨加成物
同一招）。實測 Coffee-bean 81 個區域找到 **6 對**，其中 **3 對正是操作者標註過的
4 對之一**，另外還找到他沒標的。81 個區域 → 75 個不同的化合物訊號。

**但拿它當鑑定條件沒有用**：要求「同一個化合物同時解釋 M 與 D」只讓候選少 27%，
而且在三個有標準答案的位置上**全錯**（我們給 Butanal / β-Pinene / 3-Pentanol，
操作者記的是乙酸乙酯 / 乙酸丁酯 / 2-甲基-1-丙醇）。原因就是上面那條：正確答案根本
不在漂移庫裡。所以本函式只回報配對，**不介入比對結果**。

### 相似度：比的是強度，不是峰的位置

位置只決定「在哪裡量」（把各檔的峰群聚成共用方框），真正拿來比的是每個方框量到的
**強度**。步驟：log10 → **逐檔置中**（去掉進樣量差異）→ 逐區域標準化（讓每個區域
等權）→ 相關係數。

逐檔置中是這一輪補上的：少了它，同一個標本只因為打得多一點就會被判成不像
（實測強度乘 2，相似度 0.970 → 0.673；補上後 0.989 → 0.989）。三個資料夾的
最近鄰同組驗證因此從 **41/45 → 43/45（91% → 96%）**，同組與不同組的間隔也從
+0.41 拉開到 +0.76。

**至少要 3 個檔**：只有 2 個時，逐區域標準化會把每一欄壓成 (+1, −1)，相關係數恆為
−1，與資料無關。
